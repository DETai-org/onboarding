# Issue #27: Codex + ClickUp: создание Epic Issue и плана реализации

## Контекст

Этот tutorial - второй внутри четвертого шага онбординга.

На первом tutorial четвертого шага вы выбрали и зафиксировали идею учебного проекта: что вам интересно сделать, какой смысл у этой идеи, к какому эшелону она может относиться и какой ресурс может принести экосистеме.

Теперь начинается следующий переход: от общей идеи и живой хотелки к рабочему плану действий.

Этот tutorial посвящен созданию хорошей теоретической задачи: целостного **Epic Issue** и набора **Sub-Issue / Work Package**, которые затем можно будет реализовать через ветки, Pull Request и код в репозитории `onboarding`.

Перед тем как писать код, нужно научиться формулировать рабочий план так, чтобы человек и Codex понимали один и тот же процесс.

> [!NOTE]
> Это еще не этап реализации кода. Здесь мы превращаем выбранную идею в структуру будущей работы: Epic Issue, Sub-Issue, критерии результата и будущие ветки.

Предыдущий tutorial: [Codex + ClickUp: выбор идеи учебного проекта](https://github.com/DETai-org/onboarding/issues/29)

## Перед началом

У вас уже должна быть выбранная и записанная идея учебного проекта. Если ее еще нет, сначала пройдите предыдущий tutorial четвертого шага.

Откройте и прочитайте базовые документы:

1. [Work Model](https://detai-org.github.io/Knowledge_substrate/ru/ecosystem/DETai/U.L.I/3_Technical_Standards/work-model/work-model/)
2. [Epic Issue Contract](https://detai-org.github.io/Knowledge_substrate/ru/ecosystem/DETai/U.L.I/3_Technical_Standards/work-model/issue-contract/) (наш стандарт)
3. [Методология проектного цикла DETai](https://detai-org.github.io/Knowledge_substrate/ru/ecosystem/DETai/U.L.I/2_Architecture_and_Logic/metodologiya-proyektnogo-tsikla-detai/)
4. [Codex в экосистеме DETai](https://detai-org.github.io/Knowledge_substrate/ru/ecosystem/Tools/%F0%9F%A7%ADCodex/)

Особенно важно понять связку:

```text
Epic Issue -> Sub-Issue / Work Package -> Acceptance Tasks -> Implementation Steps
```

И рабочее правило:

```text
1 Work Package = 1 branch = 1 Pull Request
```

> [!TIP]
> Если документ кажется слишком теоретическим, попросите Codex объяснить его применительно к вашей выбранной идее проекта.

## Идея проекта

Для этого tutorial не нужно придумывать идею с нуля. Возьмите черновик, который вы записали на предыдущем tutorial, и используйте его как входные данные.

Идея может быть еще неровной: бот, маленький pipeline, CLI-инструмент, parser или generator, мини-сервис, onboarding automation tool, диагност, геймификация или другой небольшой проект в `onboarding/Sandbox`.

Важно, чтобы теперь по этой идее можно было создать **Epic Issue** и несколько **Work Package**. Если идея пока слишком широкая, задача этого tutorial - сузить ее до учебного проекта, который реально пройти через полный рабочий цикл.

## Что нужно создать в ClickUp

Структуру учебного проекта нужно создавать в папке [Sandbox GitHub](https://app.clickup.com/90152202658/v/f/901515796187/90159899687) внутри space `Onboarding`.

Порядок такой:

1. В папке `Sandbox GitHub` создать новый list. Название можно выбрать под свой учебный проект или ник, чтобы было понятно, чья это рабочая песочница.
2. Внутри этого list создать главную задачу проекта - **Epic Issue**.
3. Внутри Epic Issue создать **3-4 Sub-Issue**.
4. Для каждой Sub-Issue указать:
   - purpose;
   - scope;
   - out of scope;
   - Acceptance Tasks;
   - Implementation Steps;
   - branch;
   - будущий Pull Request.

Sub-Issue в нашей модели - это не просто маленькая подзадача. Это **Work Package**, то есть самостоятельный кусок работы, который должен завершаться отдельной веткой и отдельным Pull Request.

## Как работать с Codex

Создание Epic Issue и Sub-Issue - это коммуникационная работа с Codex.

Не нужно ожидать, что первая версия плана сразу будет идеальной. Обычно Codex сначала создает полезный черновик, но он может быть слишком общим, слишком плоским или не до конца соответствовать Work Model. Это нормальная часть процесса.

Рабочий сценарий такой:

1. Дайте Codex выбранную идею проекта и ссылку на предыдущий tutorial.
2. Попросите его прочитать Work Model и методологию проектного цикла.
3. Попросите создать Epic Issue и несколько Sub-Issue в ClickUp.
4. Прочитайте результат как человек, который потом будет по нему работать.
5. Оставьте комментарии в ClickUp: к задаче, к Sub-Issue или к конкретному фрагменту описания.
6. Попросите Codex перечитать комментарии и сделать вторую итерацию.
7. Повторяйте, пока структура не станет достаточно ясной для реализации.

> [!NOTE]
> Комментарии в ClickUp - это часть процесса. Они показывают, как план улучшается через диалог человека и Codex.

## Human-only действия

Иногда внутри Work Package появляются действия, которые Codex не может выполнить сам.

Например:

- создать Telegram-бота через BotFather;
- получить токен;
- подтвердить действие в интерфейсе;
- выдать доступ к сервису;
- проверить результат глазами;
- выбрать аккаунт или организацию.

В таких случаях Codex может создать отдельный subtask внутри Sub-Issue и назначить его человеку.

> [!WARNING]
> Токены и секреты нельзя коммитить в репозиторий и нельзя вставлять в публичные GitHub issue, Pull Request или комментарии. В репозитории должен быть только пример, например `.env.example`, а реальные значения хранятся безопасно.

## Пошаговое прохождение tutorial

### Шаг 1. Возьмите выбранную идею

Откройте запись из предыдущего tutorial: название идеи, почему она интересна, предполагаемый эшелон, предполагаемый ресурс и вопросы.

Если идея слишком широкая, попросите Codex помочь сузить ее до учебного проекта, который можно реализовать в `onboarding/Sandbox`.

### Шаг 2. Дайте Codex контекст

Откройте Codex в проекте `onboarding` и передайте ему:

- ссылку на этот tutorial;
- ссылку на предыдущий tutorial с вашей идеей;
- ссылку на Work Model;
- ссылку на методологию проектного цикла;
- вашу выбранную идею проекта.

Попросите Codex создать структуру Epic Issue и Sub-Issue в ClickUp.

### Шаг 3. Проверьте первую версию плана

Откройте созданный Epic Issue и все Sub-Issue.

Проверьте:

- есть ли у Epic Issue понятная цель;
- сохраняется ли связь с исходной идеей;
- выглядят ли Sub-Issue как Work Package;
- не являются ли Acceptance Tasks слишком мелкими;
- есть ли внутри Acceptance Tasks numbered Implementation Steps;
- понятно ли, какая ветка и какой Pull Request будут связаны с каждым Work Package.

### Шаг 4. Оставьте комментарии

Если план выглядит слабым, слишком абстрактным или слишком плоским, оставьте комментарии прямо в ClickUp.

Можно комментировать всю задачу, отдельную Sub-Issue или конкретный фрагмент описания.

Пример комментария:

```text
Этот checkbox слишком мелкий. По Work Model он должен быть Acceptance Task, то есть проверяемым результатом, а не действием уровня "создать файл".
```

### Шаг 5. Попросите Codex сделать вторую итерацию

Попросите Codex прочитать ваши комментарии и переписать Sub-Issue.

Цель второй итерации - получить такой план, по которому уже можно начинать реализацию: создавать ветки, писать код и открывать Pull Request.

## Критерий завершения

Tutorial считается пройденным, когда:

- в ClickUp создан Epic Issue под выбранный учебный проект;
- внутри Epic Issue создано 3-4 Sub-Issue / Work Package;
- каждая Sub-Issue описывает самостоятельный кусок будущей реализации;
- Acceptance Tasks сформулированы как проверяемые результаты;
- под Acceptance Tasks есть Implementation Steps;
- для каждого Work Package понятна будущая branch;
- понятно, какой Pull Request должен будет закрыть каждую Sub-Issue;
- при необходимости оставлены комментарии и проведена хотя бы одна итерация улучшения плана;
- human-only действия вынесены в отдельные subtask и назначены человеку.

## Результат

После прохождения tutorial у участника будет не просто идея, а согласованный план реализации: Epic Issue, несколько Work Package и понятная дорожная карта будущих Pull Request.

Следующий tutorial четвертого шага будет уже практическим: участник создаст свою папку проекта внутри `onboarding/Sandbox`, заведет ветку под первый Work Package и начнет реализовывать код по согласованному плану.

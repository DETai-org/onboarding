# Поля и точные выборки

[← Начать работу](../SKILL.md)

Настройка полей принадлежит Web: человек создаёт определение в Space/Folder/List
и явно подключает его к выбранным спискам. Автоматического наследования нет.
MCP читает схему и работает со значениями; не создаёт определения или привязки.

1. Разреши нужный List, затем вызови `get_container` с `includeSchema=true`.
   `schema.fields` содержит подключённые поля, включая незаполненные, UUID, тип,
   варианты, обязательность, ограничения по типам задач и область определения.
   Не выводи существование поля только из значений отдельных задач.
2. Для изменения прочитай запись и передай `properties: {"UUID поля": значение}`
   в `update_work_item` с её `expectedVersion` и согласованным `confirm=true`.
   Остальные свойства сохраняются, `null` очищает значение. Number — decimal-строка;
   Select — UUID варианта; Multi-select — массив UUID; Checkbox — boolean.
3. Для поиска используй `list_work_items`: `containerId` списка либо Space/Folder
   с `descendants=true`. Разные условия соединяются через AND, массив значений
   стандартного поля — OR. Например, `priorities:["high"]` вместе с
   `properties:[{"propertyId":"UUID поля","op":"is_empty"}]`.
   Условия пустоты применяются только к спискам, где поле подключено.
4. Ответ компактный, без Markdown. `count` — размер страницы, не общее число
   совпадений. Продолжай по `nextCursor` с неизменными фильтрами; полное описание
   конкретной задачи читай через `get_work_item`. Между страницами данные могут
   меняться: это живая выборка, не фиксированный снимок.

Не угадывай UUID одноимённых полей: учитывай область и тип. Для задач разных List
проверь применимость определения, а не только совпадение названий. После изменения
настроек в Web перечитай схему; обновление пакета или reconnect не требуется.
Личные Tasks пока не поддерживают кастомные значения в Core; не обещай их запись.
Notes и WorkLogs сохраняют собственные инструменты записи и контракты.

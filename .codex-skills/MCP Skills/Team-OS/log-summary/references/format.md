# Формат рабочей сводки

[← Skill log-summary](../SKILL.md) · [← Каталог skills](../../README.md)

Это шаблон текста, не storage schema. Project ID, workDate, timezone,
createdBy/updatedBy, contributors, source channel, draft/final, timestamps,
version и source references обслуживает Core. Не повторять их вручную
в редактируемом YAML над тем же текстом. При экспорте metadata генерируется.

## Короткий завершённый блок

Пиши результат в форме: вход → выполненное действие → что теперь стало возможно.
Обычно достаточно заголовка с временем в timezone записи и 1–3 пунктов.
Одна ссылка «Где смотреть» ведёт к owning artifact, задаче или проверке.
Blocker и следующий gate — одной строкой, когда они действительно есть.
Не добавляй промежуточному блоку итог дня и не повторяй прежние результаты.

## Дневная сводка

```markdown
## Ход работы

### <время> — <завершённый результат или решение>
- <что изменилось>
- [Где смотреть](<разрешённая ссылка на evidence>)

## Связанные логи
- <ссылка на отдельно затронутый проект, только при совместимой аудитории>

## Открыто
- <подтверждённый blocker или следующий gate>

## Итог дня
<одно предложение: что стало готово или возможно>
```

Пустые разделы опускаются. `Итог дня` нужен при явном закрытии, не в каждом
checkpoint. Не дублировать в нём весь перечень хода работы.

Формулировка `🎯 КВЦ дня достигнута: …` допустима только если цель действительно
определена и результат подтверждён. При частичном результате написать это
прямо; при отсутствии КВЦ не придумывать её ради оформления. Число commits,
прошедших тестов и потраченное время сами по себе не доказывают достижения цели.

Не копировать raw output, hardware inventory и specifications. Технические
детали остаются в своём источнике, сводка содержит результат и ссылку.
Для более развёрнутого рассказа требуется соответствующий запрос; стандартный
WorkLog должен оставаться компактным и пригодным к недельной агрегации.
